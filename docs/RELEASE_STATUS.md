# LIFEOS release status — 18 September 2026

## Verdict

LIFEOS runs locally in live mode with five verified provider read connections. A separate password-protected **live Railway service** now runs the current source at `https://lifeos-live-production.up.railway.app`. It passed public login, empty-state, write/read-back, service restart persistence, cleanup, and browser UI checks. It is **not yet a completed live cross-provider product**: the hosted Google owner has no grant, the registered OAuth client rejects the new callback URI, and hosted WhatsApp automation is disabled. The older `lifeos-public` service remains a protected demo. The Windows installer is a local desktop companion, not a self-contained backend release.

## Verified on the current source

- Google consent is stored for the local owner. Gmail, Calendar, Drive, Discord and the configured WhatsApp chat returned `read_access_verified` on the live connection check after a competing browser process was stopped. A profile lease now prevents two WhatsApp workers from opening the same Chromium profile at once.
- The Electron window hosts the actual Discord and WhatsApp websites in separate, sandboxed `WebContentsView` sessions. Google OAuth opens in the system browser; the callback is bound to a one-use owner state. The packaged Windows executable visibly rendered the signed-in Discord website on 18 September. The packaged WhatsApp view and account persistence after restart still need acceptance checks.
- The live **My work** screen starts empty and persists projects, goals, tasks, habits, notes, dated habit check-ins, linked progress, a 14-day local agenda, work-history activity and due reminders. Google Calendar events appear in that agenda when the live Google API is available. None of these live records are seeded or simulated. The dashboard fetches one owner-scoped snapshot per navigation to stay below the request limit. Link options include all saved projects, goals and tasks; a regression covers an older project after more than 100 records.
- Data export includes work records, activity and reminder acknowledgements without exporting OAuth tokens. Owner deletion removes them with the rest of the workspace. A schema revision adds an owner/kind/time index for history queries. New audit entries query only the latest chain record, and a 102-project regression verifies the chain.
- Google Maps/Routes API calls and keys were removed from source. Plans state when travel time cannot be determined; no route estimate is invented.
- Verification passed with 110 backend tests, 14 Chromium browser tests, two desktop navigation tests, Python lint, focused mypy, frontend lint/build, source secret scan and desktop dependency audit. The optional external public-demo browser check is skipped without release credentials. The Windows installer is 111,413,331 bytes with SHA-256 `F6417BEB786CE7E764F605A584B4385BA5D86A25F970149F005313072BDC809E`; Windows reports `NotSigned`. The source archive is `artifacts/lifeos-source.zip` with its adjacent SHA-256 file.
- A pinned-base Docker image built as `lifeos:release-candidate-20260918` (manifest `sha256:29c2cefbf9b8fbbda667fd6029ff3d664c95dacccbe06a12736e1c0b60ed0e52`). An isolated live-mode SQLite container started with zero work records and saved a real task. An isolated PostgreSQL 17 container retained a task across an application container restart and reported schema revision 2. These test containers and their network were removed afterward; this is local release evidence, not public deployment.
- A byte scan of the release-candidate image's backend and compiled frontend found zero Maps/Routes endpoint or key references. The protected Railway demo has not received that image.
- A new `lifeos-live` service deployed successfully in Railway's EU West region with its own `/app/data` volume and HTTPS domain. `/health` reports `mode=live`, `/ready` passes, and unauthenticated work access returns 401. A temporary task created through the public API survived a service restart and a second login; it was deleted afterward, leaving zero tasks. The deployed desktop-width browser UI passed login, My work empty state and Integrations navigation; a 390-pixel viewport passed the mobile menu, My work, Calendar and no-horizontal-overflow checks. A live provider check reported Discord `read_access_verified`; Gmail, Calendar, Drive and WhatsApp were `not_connected` on this hosted owner. A Google authorization request returned `redirect_uri_mismatch` for the hosted callback, so owner consent cannot complete there until that redirect is registered.

## Release blockers

1. **Hosted Google consent:** add `https://lifeos-live-production.up.railway.app/api/integrations/google/callback` to the OAuth web client's authorized redirect URIs, then complete owner consent in the hosted app and verify Gmail, Calendar and Drive. The separate `lifeos-public` URL remains the older demo.
2. **Same-view WhatsApp execution:** the visible Electron WhatsApp page and the approved Playwright sending profile are separate sessions. A hosted device bridge through the visible page, with replay protection and read-back, is not implemented.
3. **Live cross-app acceptance:** no single approved event has yet updated Calendar and sent both Discord and WhatsApp notifications with independent read-back on the current revision. The hosted service cannot run WhatsApp browser automation; read-access checks cannot substitute for this proof.
4. **Desktop release:** an unsigned Windows companion installer has been built. It needs the local live backend at `127.0.0.1:8010`. The packaged executable rendered signed-in Discord; packaged WhatsApp and restart persistence remain unverified. It is not signed with a publisher certificate.
5. **Production scale:** the supported deployment is one owner and one backend process. Dedicated account registration, owner-specific Discord/WhatsApp configuration, horizontal workers, hosted backups and load acceptance are not complete. Do not claim thousands-of-users readiness.
